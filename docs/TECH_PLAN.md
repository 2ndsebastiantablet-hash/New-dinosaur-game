# CLOSING TIME: Technical Plan

This is the Phase 0 plan required by GDD Section 18 and Amendment A8. It sets out
the engine stack, how the game gets built and installed with no desktop computer,
and the milestones up to the first playable build (GDD Section 20).

## 1. Constraints

| Constraint | Consequence |
|---|---|
| Target headsets: **Meta Quest 3 and Quest 3S** | Android/ARM64, OpenXR, standalone performance budget (72–90 Hz, mobile GPU). |
| The developer works **from a phone only**: no Unity Editor, no PC | Nobody can open the Unity Editor. The project has to be authored entirely as text (C#, JSON, package manifest, project settings) and built in the cloud. |
| The coding agent's container **cannot reach Unity's servers or a headset** | The code can't be compiled or tested before each push. Every iteration goes: push → cloud build → install on Quest → report back. Compile errors arrive through the cloud build log. |
| Packages must resolve from `Packages/manifest.json` alone | Only UPM packages (Unity registry or scoped registries). Nothing that has to be imported by hand as a `.unitypackage` through the Editor. |

## 2. Stack

| Area | Choice | Why |
|---|---|---|
| Engine | **Unity 6 LTS** (6000.0 series), Built-in render path → URP once the pipeline is proven | LTS version supported by Unity Build Automation. |
| XR | **OpenXR** + **Unity OpenXR: Meta** (`com.unity.xr.openxr`, `com.unity.xr.meta-openxr`) | Officially supported Quest path, pure UPM. |
| Input | **Input System** (`com.unity.inputsystem`) reading OpenXR controller poses and buttons | No Editor-authored rigs needed. |
| Locomotion | **Custom arm-swing physics rig**, written from scratch | GDD 8.1. XR Interaction Toolkit's locomotion doesn't fit this model. |
| Grabbing | **Custom grab/physics system** | Has to be built around network ownership anyway (GDD 11.4). |
| Networking | **Netcode for GameObjects**, host-authoritative | GDD 11.4 explicitly allows host-authoritative for the first build. Pure UPM. (Photon Fusion was ruled out because it ships as a `.unitypackage` that has to be imported in the Editor.) |
| Lobby / connection | **Unity Gaming Services: Multiplayer Services** (Lobby + Relay) | Join by lobby code without port forwarding. Free tier. |
| Voice | **Vivox** (`com.unity.services.vivox`), proximity channels | GDD 11.3. Free tier. Comes after movement and sync are stable. |
| Content data | **JSON** files in `Assets/Resources/Data/` loaded into C# definition classes | GDD 16 requires data-driven content. JSON can be edited from a phone and needs no Editor-generated GUIDs. |
| Scenes / prefabs | **Generated by editor scripts at build time** (Build Automation pre-export method), plus runtime procedural construction from layout data | Avoids hand-writing fragile scene/prefab YAML. Network prefabs are created with `PrefabUtility` before the build so Netcode gets stable prefab hashes. |

## 3. Build and install pipeline (phone-only)

1. **Code** is pushed to this GitHub repo.
2. **Unity Build Automation** (cloud.unity.com, usable from a phone browser) is linked to the repo and builds an Android APK on its Windows build machines. The free tier includes a monthly allowance of build minutes. If that turns out to be insufficient, the fallback is GitHub Actions + GameCI, but Personal-license activation there is unreliable without a computer.
3. **Install on Quest**, one of:
   - **Meta Horizon developer dashboard → release channel**: upload the build and invite the team's Meta accounts. Testers install it like a normal store app. This is also how 5–10 friends get the game.
   - **Sideload from an Android phone** over USB-C with an ADB app (e.g. Bugjaeger). Doesn't work from an iPhone.
4. **Developer mode** on the headset is turned on from the Meta Horizon phone app (requires a free Meta developer organization).

Accounts the developer needs to create: Unity account (+ Unity Cloud project, which also provides Lobby/Relay/Vivox) and a Meta developer organization. All of these can be created in a phone browser.

## 4. Milestones

Each milestone ends in an installable build that's tested on a Quest before scope expands (GDD 23). Multiplayer tests need 2+ headsets. The **5-player minimum is enforced in normal matches but bypassable through a developer setting** so 1–4 player testing works (GDD 20 calls for 1–4 initially).

| # | Milestone | Exit criteria |
|---|---|---|
| **M0** | **Pipeline proof**: minimal project (manifest, settings, generated boot scene), grey room, tracked head + controller hands | Cloud build succeeds; APK installs and runs on Quest 3/3S at native refresh rate. |
| M1 | Arm-swing locomotion + collision, comfort options (vignette, snap/smooth turn) | Can move, climb small ledges, no sickness spikes. |
| M2 | Grab/throw physics objects; Netcode host/client; Lobby code join via Relay; avatar head/hands sync; name labels | 2+ players see each other and pass a box back and forth. |
| M3 | Grocery store graybox generated from layout JSON (zones per GDD 7.1); preparation state; OPEN STORE control; 10-minute timer; prep-phase task locks (A2) | Players navigate the store; prep → open → close loop runs. |
| M4 | Role assignment (5 mandatory roles, A1; unique roles); tasks: stock shelf, clean spill, checkout; shared task board | Each role has work; tasks complete and network correctly. |
| M5 | Customers: Routine, Impatient, Confused + Spill-Prone, Coupon Dispute, Lost Child; five-star rating with penalties/recovery | Rating changes for understandable reasons. |
| M6 | Nine-day campaign state, Store Funds, 2–3 upgrades, day curves (Threat/Chaos budgets, A4) | Full week can be played; days escalate. |
| M7 | Rats or flies, Shoplifter, Mimic Customer, one-star District Manager fail sequence | First playable build per GDD 20 is complete. |
| M8+ | Remaining Amendment 1 items in A7 order, then GDD Phase 7–8 | — |
